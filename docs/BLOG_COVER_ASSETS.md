# Persistent content image assets

This describes the 0.36.0 source; see the [delivery record](releases/0.36.0.md) for actual publication status. It is not included in 0.35.0. No new site-config fields or dependency are added. Blog List, tag archives sharing `BlogCards`, the article's main cover, and local Fragment images use the same persistent store. Homepage avatar GIFs, article-body images, related-card images and unrelated media keep their existing processing.

## User-owned inputs and persisted outputs

Existing `heroImage` paths stay valid, including images beside Markdown/MDX posts and in `src/assets/blog/default-covers/`. Users may also keep new originals in `src/assets/blog/covers/originals/` and reference them through ordinary `heroImage` frontmatter. Dropping an image there prepares its variants; it does not create or publish an article, or change the existing new-post default-cover selection. The generator scans both cover pools and local article references, deduplicating shared references across translations. Only referenced variants are copied to the deployed output.

```text
src/assets/blog/covers/
  originals/       # optional originals; existing covers need not move
  generated/      # persisted WebP derivatives, committed to Git
  manifest.json   # source hashes, recipe and output dimensions/hashes
```

Run `npx @anglefeint/astro-theme prepare-covers` locally; `--check` validates without writing. Dev startup and changes to originals/article references prepare missing or stale variants automatically. Local `doctor` also prepares before retaining its existing Astro check/build/About assertions, so a supported local upgrade from an older package can create the initial assets. With a truthy `CI` other than `false`/`0`, doctor only validates. Plain `astro build`/`npm run build` and config sync always validate; they never resize/encode a cover. Commit the original files and the entire generated folder/manifest before deployment. Missing, changed or corrupted assets fail with a preparation command instead of silently regenerating on the host.

The CLI follows the standard `src/` and `public/` project layout; the integration uses Astro's configured root/srcDir/publicDir/base. Projects with custom source/public directories or base-prefixed source references should prepare via the configured dev server. Do not add a second image configuration to site-config or generate replacement originals under public.

## Recipe, validity and lifecycle

The initial recipe generates widths 400/640/800/960/1200 plus a capped source width when needed, never enlarging a small source. It auto-orients raster pixels from EXIF and preserves the original aspect ratio; existing 4:1/2.4:1 leading-card and ordinary-card CSS controls visible cropping. WebP quality 80/effort 4 retains the existing encoder-quality target; it is not a claim of lossless resize or compression. Originals are never recompressed or replaced. SVG and multi-frame images remain passthrough originals to avoid rasterizing vectors or flattening animation.

Names include a sanitized basename, source-path hash, original-content hash, recipe hash and width. Identical basenames in different directories cannot collide; content or recipe changes get different URLs. The manifest records SHA-256 of each output. Normal preparation reads hashes and reuses valid variants without touching bytes/mtime; it regenerates only missing/corrupted variants, or the affected source's variants after source/recipe changes. A check never repairs files and does not need the Astro cache. Unreferenced/older generated files are not automatically deleted, and checks ignore obsolete entries not needed by current sources. Remove unused generated files deliberately rather than deleting user-owned source directories automatically.

Output writes are atomic within the project; linked output/source paths cannot escape the project. CI/build validates source checksums, the recipe signature, expected widths and output hashes without running the encoder. The build copies referenced pre-generated bytes unchanged to `dist/_blog-covers/`; conflicting output bytes fail rather than overwrite custom files. Deployment uses ordinary static assets, not an image server or deployment cache. Dev serves this same namespace, debounces/serializes preparation and disposes the watcher on server shutdown.

## Rendering and priority

`BlogCards.astro` resolves each entry through its public collection `filePath`, using a build-only virtual manifest. Plain `<img>` elements use the persisted URLs, `srcset`, layout-specific `sizes`, async decode and reserved dimensions; they do not call Astro Image for a second conversion. The first two actual covers on each archive page are native eager/high-priority candidates, covering the desktop leading image and mobile's next-card LCP. Remaining images stay lazy/auto. This is limited to two candidates, not a guarantee of which image Lighthouse will select.

Native eager loading can fetch those two candidates even when a saved List preference hides the images; avoiding that completely would require client-controlled discovery and delay or complicate the native image path. The initial implementation favors direct discovery and predictable card-view LCP, without adding image-loading JavaScript. Cards/List layout, user preference, pagination, tags and visual effects remain unchanged. Synthetic callers without a collection filePath and SVG/animated covers use the supplied original URL.

The package article route passes `post.filePath` to `BlogPost.astro`, which renders the primary cover with persisted srcset/sizes, reserved original dimensions and eager/high priority. Existing desktop 3:1 and mobile 2:1 CSS cropping is preserved. Its Canvas draws from that same DOM image after load, using natural pixel dimensions; no independent original-image request is made. Cached images, responsive source changes and disposal retain their normal lifecycle. The existing 1200px maximum variant bounds download size; choosing a candidate remains the browser's DPR/sizes decision. Custom layout callers without filePath retain the supplied original URL.

## Fragment images

Keep existing Fragment Markdown image links, reference-style images and raw HTML `img` links. A root path such as `/images/fragments/photo.png` reads `public/images/fragments/photo.png`; a relative path reads from the Markdown file's directory. Public originals stay in place. Remote/data URLs are not downloaded by preparation; SVG and animation keep their original formats. Do not infer references from fenced/inline code or frontmatter. Missing supported local image files fail preparation clearly; linked sources cannot escape the project.

The existing `prepare-covers` command now prepares these images too. Dev watches referenced public images as well as content/source assets; local doctor prepares, and build/config sync/CI doctor only validate. Commit Fragment originals plus the same `src/assets/blog/covers/manifest.json` and generated files. The directory name is retained for compatibility; a separate Fragment derivative folder or new setup step is not required. Only currently referenced variants deploy, including images referenced exclusively by Fragments.

The documented Satteri MDAST plugin replaces supported local image nodes with stable source markers before Astro's image conversion. Feed and Home render those markers using current manifest data and remove them from delivered HTML. This keeps image-only edits fresh without embedding stale hashed URLs in cached Markdown output. Final `img` elements receive srcset/sizes, async decoding and missing width/height; explicit author dimensions remain, with the missing counterpart calculated from the source ratio. The first image of each feed page is eager/high, remaining feed images and homepage thumbnails are lazy. Homepage thumbnails reuse the generated candidates with their own smaller sizes hint. Remote images retain their source and author dimensions; relative vector/animated Markdown images retain Astro's existing path handling.

Feed math CSS is included only if enabled and the current page's rendered cards contain formula markup. Other pages' formulas do not force it onto a plain page. Text, code, comment controls, anchors and pagination remain unchanged. Tests: `tests/fragment-images.unit.test.mjs`, `tests/fragment-images-render.test.mjs`, `tests/fragment-preview-render.test.mjs` and the existing fragments static-render suite.

## Module boundaries

The image integration owns preparation, its cached manifest snapshot, the virtual-module adapter and Markdown processor configuration. The root integration only supplies the existing mathematics flag; it does not store image data or broker callbacks between modules. A snapshot updates once per preparation, rather than rebuilding all image data for every Markdown document.

| Module                                          | Responsibility                                          | Dependency boundary                                                         |
| ----------------------------------------------- | ------------------------------------------------------- | --------------------------------------------------------------------------- |
| `covers/fragment-sources.mjs`                   | Extract source references and resolve local paths       | Preparation/source inspection; no Satteri compiler or page renderer         |
| `covers/fragment-markdown.mjs`                  | Adapt source references to stable Markdown markers      | Public Satteri plugin API; no image encoding or final page rendering        |
| `covers/fragment-render.mjs`                    | Turn markers into final image HTML                      | HTML and supplied manifest only; no filesystem, Markdown parser or compiler |
| `covers/responsive.mjs` and `covers/types.d.ts` | Shared image selection/srcset and manifest types        | No page markup, route queries or encoding; callers retain layout/priority   |
| `covers/integration.mjs`                        | Coordinate the above at Astro/Vite lifecycle boundaries | State stays private; pages consume virtual data and rendering helpers       |

`utils/blog-cover.ts` remains the collection-filePath adapter for BlogCards/BlogPost and delegates selection to the same responsive helper. Feed priority remains in `utils/fragment-html.ts`; thumbnail sizes remain in FragmentSignal. These policies differ by context and do not belong in the encoder. The shared image store/encoder and its persisted-file contract remain unchanged.

## Decisions and limits

| Decision                                                      | Reason                                                                                                   | Practical limit                                                                                                                  |
| ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Persist variants and hashes in the project                    | Missing files can be repaired locally; deployment copies validated bytes without relying on a host cache | Commit originals, manifest and generated files together; this applies to these image paths, not every media pipeline in the site |
| Preserve aspect ratio and use CSS for visible cropping        | One source can serve archive, detail and Fragment contexts without destructive crops                     | Width selection is responsive; it does not choose an alternate composition or focal point                                        |
| WebP quality 80, capped at 1200px                             | Reuse the existing modest-size encoding target with a bounded candidate set                              | Resizing/re-encoding is lossy; high-DPR large displays are bounded by the maximum candidate; originals remain available          |
| Share selection and encoding, keep layout/priority in callers | Feed, article and thumbnail layouts have different needs                                                 | Two archive candidates or one feed candidate are heuristics, not a guarantee of Lighthouse's chosen LCP element                  |
| Render stable Fragment markers against current data           | Replacing an image need not change Markdown to get the new hashed URL                                    | Pages must use the renderer; a marker is an internal compilation detail, never a public image URL                                |
| Reuse the DOM hero image in Canvas                            | Avoid loading the original independently from the responsive cover                                       | Draw using natural dimensions; redraw after source changes and remove listeners on disposal                                      |

No network image service, runtime encoder or extra theme toggle is introduced. Remote images retain their author's URL/dimensions; the local preparation command cannot fix their payload or infer remote dimensions. Supported relative SVG/animated Markdown paths retain Astro handling. A synthetic custom BlogPost caller without collection filePath uses its original image URL instead of guessing a manifest entry.

## Troubleshooting

| Symptom                                                | Check and action                                                                                                                                                                                                                                     |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Build reports missing/stale/modified derivatives       | Run local `prepare-covers`, or configured dev for a custom directory layout; review and commit the source/manifest/generated changes. Do not bypass the check or regenerate on deployment                                                            |
| A new public Fragment image is not prepared            | Reference it in an actual Fragment Markdown/HTML image. Public is not scanned as a general image library; source pools and actual references define the inventory                                                                                    |
| Output still uses the original                         | Check whether the source is remote, vector/animated, a relative passthrough, or a custom layout lacking filePath. These fallbacks are intentional                                                                                                    |
| Replacing a source appears to show an old image        | Check the generated source/content hash and current manifest. During development of the pipeline itself, stop an older dev process before preparing with changed code, then restart; an old in-memory implementation can overwrite a newer inventory |
| Many old generated files remain                        | Obsolete/unreferenced files are deliberately not deleted automatically. Review cleanup separately; current references alone determine copied build output                                                                                            |
| A generated URL works locally but not after publishing | Deploy all static output, including `_blog-covers`; preserve the configured base path. Do not copy only HTML                                                                                                                                         |

Read-only diagnosis: `npx @anglefeint/astro-theme prepare-covers --check`. A check does not repair files. A passing hash/build check proves file consistency and rendering contracts; it does not establish image taste, exact browser candidate selection or a PageSpeed improvement.
