# 0.10.0 — Optional Google Analytics 4

## Status

Release preparation; not yet published. Validation and delivery evidence will be recorded below.

## Changes

- Configure one top-level `analytics.googleAnalyticsId` in `src/site.config.ts`; omitted/empty is off. Use the Web stream Measurement ID (`G-...`), not a property name or numeric ID.
- Cover all languages and shared themed layouts through ThemeFrame, without SEO or route edits. Static redirect documents are not tracked.
- Validate ID format; include the loader only in production builds. Skip localhost, `.localhost`, loopback and `0.0.0.0` previews. Remote/LAN previews still track.
- Queue one automatic page-view configuration and load the official Google script asynchronously. Preserve existing consent commands/dataLayer. No manual duplicate page_view, new runtime dependency, consent banner or automatic Consent Mode setup.
- Document setup, duplicate-installation precautions, consent responsibility and preview behavior in all nine READMEs.

## Upgrade

The complete feature needs the matching starter schema, defaults and theme adapter. npm alone does not update these files. Follow [UPGRADING.md](../../UPGRADING.md) and migrate content/personal settings into a fresh matching starter for the supported baseline. The `^0.9.x` range does not include `0.10.0`. No article or page-route changes are required.

Leave the ID empty until ready to enable collection. Rebuild and redeploy after changing it; visit the production site and check GA4 Realtime. Arrange any required consent management first, and avoid tracking the same site twice through GTM, Zaraz or a separate snippet. Real GA ingestion requires the user's own property and is not established by mocked/local tests.

## Validation and delivery

The initial publish dry-run was stopped by the dependency audit: [GHSA-hp3w-g68c-fv3c](https://github.com/advisories/GHSA-hp3w-g68c-fv3c) affects `sprintf-js`, pulled into main's documentation tooling through `gray-matter → js-yaml 3 → argparse 1`. No patched sprintf-js version was listed when reviewed. Remove that maintainer-only dependency chain and use the already compatible `js-yaml` 4 parser directly through a small shared YAML-frontmatter extractor. This does not change Astro's content parsing, the theme package dependencies or the starter dependencies. The audit gate is unchanged.

- Lint, 83 unit tests and metadata validation for 64 maintained documents passed. Main full checks passed with 0 Astro errors/warnings (48 existing hints), 190 pages, 126 indexed articles and nine About runtime checks.
- Independent packed-starter installation/audit and 14 builds passed, including six default locales × both prefix modes, all nine languages, GA enabled/disabled, and existing search/tags/music/share-image regressions.
- 34 existing Chromium E2E tests passed. A separate temporary Astro fixture verified actual production HTML, blocked-Google behavior in Chromium, localhost/IPv4/IPv6 guards, disabled output, invalid-ID build failure and exclusion in configured dev mode. No test sent analytics to Google. The fixture's initial Windows CLI/cache setup errors were corrected before the successful run.
- Release dry-run/publication may reuse the completed main/build-matrix checks via `--skip-checks`; mandatory dependency audits and isolated package installation/CLI checks still run. Pre-push runs the final full main check again after the maintainer dependency change.
- Documentation review updated nine READMEs, package README, architecture, upgrade guidance, metadata parser reference and release records. Visual systems, SEO/i18n guides and existing article guides required no behavioral rewrite; the feature changes no visual design, route semantics or writing commands. Existing managed configuration files were already in the starter manifest; new runtime files are included by the package's existing component/script/utils file groups. The new parser is maintainer-only.
- Limitations: GA4 property ingestion needs the user's deployed site and real ID; Firefox/WebKit and pnpm were not rerun for this feature. Cloudflare account-side branch/deploy settings are not directly inspected; successful GitHub build status and later live-site inventory checks are separate evidence, not proof of those settings.
