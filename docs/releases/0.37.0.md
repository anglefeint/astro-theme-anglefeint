# 0.37.0: Brood War atmosphere for Fragments

This ledger defines the release changes and selected checks; it does not claim publication or demo acceptance before delivery completes. Exact source/npm/starter identities, technical results and timings belong in ignored maintainer-session evidence and the [GitHub Release](https://github.com/anglefeint/astro-theme-anglefeint/releases/tag/v0.37.0). The previous release baseline is 0.36.2.

## Changes

- Fragments adopts a static volcanic-world/orbital-deck scene, transparent temple-framed cards and a sticky transparent title row. Route-local controls borrow dark alloy, restrained energy and organic shading from the original StarCraft: Brood War references without changing shared pagination or scroll behavior.
- A small route-owned chrome observer tracks navigation/title heights and cleans up on navigation/pagehide. Stable fragment IDs, share links, localization, copy controls and the feed's complete Markdown rendering remain intact.
- The music player receives compact spacing, a transparent dark housing, flat track rows and native pressed-state feedback without moving button text. Playback, queue, seeking, volume and collapse logic remain shared and unchanged.
- The comment dialog uses a subdued Dark Templar/Dark Archon-inspired frame and five open Maelstrom-inspired binding strands instead of a bright sphere. Reduced motion leaves static strands. Provider readiness, timeout, retry, focus and scroll restoration remain unchanged.
- Fragments locally selects the official `noborder_gray` Giscus theme. Article comments retain the site-configured theme; no custom provider CSS, dependency patch or new package dependency is introduced.
- Blog and Tags stop rendering floating dust while keeping rain, fog and light beams. The reusable dust component remains available, and the adapter accepts rain and dust roots independently.
- Nine README translations describe the six page atmospheres and concise AI guidance, and share new Fragments screenshot/promotional artwork. Main-only demo content includes additional notes, long-pagination fixtures and a nine-language short article explaining the StarCraft tribute, all sharing the supplied carrier cover; this content is not copied into consumer projects.

## Compatibility and ownership

Astro peer support advances to `^7.4.7`, and the main/new-starter dependency targets `^7.4.12`. This fixes the blocking audit findings for [dynamic tag-name injection](https://github.com/advisories/GHSA-mh32-jxcr-mh9f) and [the Node image-endpoint path check](https://github.com/advisories/GHSA-r3h5-4585-7x3w). Existing Astro 7 projects should update Astro within major 7 before the ordinary theme upgrade; see [Upgrading](../../UPGRADING.md#0370-fragments-atmosphere-and-patched-astro-7). Node support is unchanged.

No configuration field, content schema, route identity, package export or dependency is added. Fragments and its comments stay disabled by default. Existing fragments, stable IDs, personal configuration, media and custom pages remain user-owned. New installations receive manifest-owned README/gallery assets; upgrades do not overwrite personal README/content copies. The main demo retains its explicit article Giscus theme setting. Earlier background/design variants are preserved rather than silently deleted from the working tree.

## Selected technical plan

Select focused Fragments/index/chrome-cleanup/lifecycle/music unit files, lint, integration wiring, types, one main build, packed-CLI checks and one independent installed-package check level. Use metadata, repository formatting and virtual starter checks for the documentation/distribution changes. Browser regressions, live Giscus, Cloudflare polling, tutorial walkthroughs and a full installed matrix are not selected. The separately approved README screenshot is an asset capture, not a browser-regression pass.

Prepare the reviewed scope and commit message through `release:flow prepare`; review every untracked/design/demo group before staging. Keep normal hooks, the structured starter drift preflight, blocking audit, exact source/download verification and isolated starter delivery. Source handoff and announcement retain their normal plan review before execution. Never repeat an accepted npm upload; use read-only recovery if registry verification fails.
