入門ガイドの第8 / 8回です。[全ガイドの順序](/ja/blog/starter-guide-1-configure-your-site/#tutorial-order) · [設定リファレンス](/ja/blog/config-reference/)。

ローカルで起動できたら、公開には最終ドメインの確認、完全な静的ファイルの生成、そのドメインでの配信が必要です。テーマはドメイン購入、DNS 変更、ホスティングへの自動ログインは行いません。

現在の starter は静的サイトをビルドし、本番で Node.js を常駐させたり SSR adapter を追加したりする必要はありません。以下は npm と既定出力 `dist/` の例です。

## 1. 正式 URL を決める

`https://blog.example.com` など自分で管理するドメインを用意し、`src/site.config.ts` の既存の最上位 `site` に統合します。

```ts
site: {
  url: 'https://blog.example.com',
},
```

最終公開 URL を指定し、localhost、記事 URL、ホスティング管理画面は指定しません。他のサイト情報は残します。

canonical、RSS、sitemap、共有画像、公開コンテンツのリンクに使います。開発サーバーの URL は変わらず、未設定のドメインが自動的にサイトを指すこともありません。

### 古い環境変数の上書きを確認する

`.env`、適用される `.env.*`、ホスティングのビルド環境に `PUBLIC_SITE_URL` があれば設定より優先します。site.url を変えても旧ドメインならここを確認します。通常 dev は development、build は production で、独自 `--mode` は対応するモードも読むため `.env` だけでは不十分です。

不要なら環境変数を削除して site.url にまとめ、必要なら各環境で正しい値を設定します。再ビルドが必要で、旧成果物の1リンクを手作業で変えるだけでは不十分です。

### ドメインルートを使う

現在は `https://blog.example.com/` のようなルート配備が前提です。`https://example.com/my-blog/` のような配備は追加対応が必要で、Astro base だけですべてのページ・素材が対応するわけではありません。

ルートサイト、静的ディレクトリの index.html、サブページ URL を提供できるホストを選びます。GitHub Pages はサイトドメイン・独自ドメインの手順を優先し、プロジェクトのサブパス手順をこのテーマの対応済み設定と見なさないでください。[Astro 配備ガイド](https://docs.astro.build/en/guides/deploy/)の各ホスティング手順も参照してください。

## 2. 必要なソースをそろえる

自分のブログと実際に内容を管理するブランチを使い、テーマの保守リポジトリのデモをそのまま個人ブログとして配備しないでください。設定、内容、依存情報、必要な素材を含めます。

ローカルカバーや Fragment 画像を変えたら、ローカル dev または doctor でレスポンシブ画像を準備してからコミットします。

- 記事、Fragments、独自ページ、`src/site.config.ts`。
- 参照する原画像、public 画像、アイコン、実際に使う音楽。
- manifest.json、generated/、使用する originals/ を含む `src/assets/blog/covers/` 全体。
- `package.json`、`package-lock.json`、既存 Astro 設定、ホスティング設定。

元画像は originals とは限らず、記事の隣や public のファイルもコミットします。[画像ガイド](/ja/blog/starter-guide-images/)を参照してください。

**配備側の通常 build は永続レスポンシブ画像の検証・コピーのみで、補完生成しません。** CI doctor も検証のみです。不足・期限切れ・変更で失敗したら、ローカルで準備・コミットして再配備します。ホストの画像キャッシュに依存しないでください。

Git からの配備には node_modules、`.astro`、dist のコミットは不要で、プラットフォームがインストールと生成を行います。PC の依存ディレクトリをサイトとしてアップロードしないでください。環境ファイルがリポジトリにない場合はホストに必要変数を設定します。PUBLIC_ は公開情報用で秘密情報には不適切です。

## 3. ローカルで確認し、実際のビルドをプレビューする

Ctrl+C で dev を止め、プロジェクトルートで実行します。

```bash
npm run doctor
npm run preview
```

表示された URL を開き、ホーム、記事、画像、言語メニュー、検索を確認します。追加言語と任意ページの入口も確認します。コメントなど外部サービスはブラウザーの実接続が必要で、ビルド成功は外部権限の正しさを証明しません。

各コマンドの役割は異なります。

| コマンド          | 役割                                                                   |
| ----------------- | ---------------------------------------------------------------------- |
| `npm run dev`     | ローカル開発と関連画像の自動準備。ビルド済み全文索引はありません。     |
| `npm run doctor`  | ローカル画像準備、Astro 検証、ビルド。About 有効なら実行時設定も確認。 |
| `npm run check`   | 現在の starter では doctor と同じ。連続実行は不要。                    |
| `npm run build`   | サイトのビルド。永続画像は検証のみで doctor のローカル補完は行わない。 |
| `npm run preview` | ビルド済み dist を配信。再ビルドや公開は行わない。                     |

検証・ビルド失敗を先に直し、残った dist は公開しないでください。doctor 成功ならビルド済みなので、すぐ check・build を繰り返す必要はありません。preview は Ctrl+C で止めます。

## 4. 静的出力をすべて配備する

Git 連携でホストにビルドさせるか、ローカルビルドを手動アップロードできます。どちらも最終的には同じ静的出力を提供します。

### 方法1：Git からホスティング側でビルドする

選んだプラットフォームに自分のリポジトリを接続し、次を指定します。

| 項目               | 現 starter の設定                                                             |
| ------------------ | ----------------------------------------------------------------------------- |
| ビルドブランチ     | 自分がブログを管理する実際のブランチ。                                        |
| プロジェクトルート | ブログの package.json がある場所。リポジトリ最上位とは限りません。            |
| Node.js            | プロジェクトと依存の要件を満たす版。現在の starter は22.12.0以降。            |
| インストール       | npm は `npm ci`。package.json と一致する package-lock.json のコミットが必要。 |
| ビルドコマンド     | `npm run build`                                                               |
| 出力先             | プロジェクトルート相対の `dist`。                                             |

自動インストールがあるなら重ねて指定しません。全スクリプトを指定するホストでは install 後に build します。doctor・check・build を重複させたり、コミット不足を隠すために配備側の画像生成を加えたりしないでください。

フレームワーク設定、ブランチ、インストールは実際のホスト設定に従います。静的出力を選び、dev・preview を本番起動コマンドにしません。

### 方法2：ローカルビルドをアップロードする

doctor 成功後、`dist/` の全内容をサイトルートにアップロードします。フォルダー選択なら dist、ファイル選択なら dist の中身を選び、余分な dist 階層を加えないでください。

HTML 以外に `_astro/`、`_blog-covers/`、`_social/`、検索索引、今回生成された全出力を含めます。アンダースコアのディレクトリは不要な一時ファイルではありません。HTML だけでは CSS・JS・画像・検索が欠けます。

再公開は完全配備・置換の仕組みを使い、削除記事、旧ページ番号、旧言語が残らないようにします。ローカル Markdown の削除は、手動サーバーの旧 HTML を自動削除しません。

## 5. ホストにドメインを追加して DNS を設定する

ホストに独自ドメインを登録し、指定された値で DNS を追加・変更します。ルートとサブドメインはレコード種別・宛先が異なる場合があるため、例の IP をコピーせず実際の指定値を使います。

ドメインと HTTPS 証明書が有効になるまで待って正式 URL を開きます。裸ドメインと www など複数使う場合、主 URL を1つ決めて他を転送し、site.url も主 URL にします。

canonical はメタ情報でリダイレクトではありません。site.url は DNS・証明書・複数ドメイン転送を実行しません。主ドメイン変更後は再ビルド・再配備し、旧環境変数も更新します。

## 6. 公開後にページと公開出力を確認する

正式ドメインの記事 URL に直接アクセスし、再読込でも開くことを確認します。ホームからのクリックだけでは不十分です。画像、コード外観、言語切り替え、検索も確認し、dev だけで試した機能はビルド済みサイトで再確認します。

以下の静的出力は既定であり、同じ統合を重ねてインストールする必要はありません。

| URL の例                                       | 用途                                                       |
| ---------------------------------------------- | ---------------------------------------------------------- |
| `/robots.txt`                                  | クロール規則と sitemap URL。アクセス権管理ではありません。 |
| `/sitemap-index.xml`                           | サイトマップ入口。正式ドメインを使うこと。                 |
| `/zh/rss.xml`                                  | 簡体中国語の購読。他の有効言語は zh を置換。               |
| `/llms.txt`                                    | AI 可読コンテンツの総索引。                                |
| `/zh/llms.txt`、`/zh/llms-full.txt`            | その言語にエクスポート内容がある場合の索引・全文。         |
| `/zh/blog/my-first-post/index.md`              | 公開記事の Markdown。slug は実記事に置換。                 |
| `/zh/fragments/index.md`、`/zh/about/index.md` | 対応ページが有効で出力条件を満たす場合の公開内容。         |

sitemap 更新日は updatedDate、なければ pubDate で、毎回のビルドで新日付を偽造しません。無効言語・ページの出力は期待できません。search: false は非公開化でも他出力の禁止でもありません。

AI 出力は公開記事、有効な Fragments・About を含み、コメントと装飾ツール UI は含めません。実 noindex や外部 canonical は除外します。ユーザーファイルと出力先が競合するとビルドを止め、上書きしません。発見リンクと出力は再ビルドで更新し、一緒に配備します。

発見と読み取りを助けますが、検索登録・AI 引用・訪問増を保証するものではありません。

### ホスティングのレスポンスヘッダー

ビルドはソース public/_headers を変えず、既存規則を維持して dist/_headers の `/:locale/terminal/*` に `X-Robots-Tag: noindex` を追加します。対応ホストは適用し、他ホストは同等の設定が必要です。

Astro preview は _headers を再現しません。適用確認は正式サービスのレスポンスで行い、ローカルファイルの存在だけでは判断できません。このための Node サーバー追加は不要です。

ドメインと環境変数の優先順位は[サイトリファレンス](/ja/blog/config-site-chrome/#environment)、公開説明は[GA4 と AI 補足](/ja/blog/config-analytics-ai/#supplement)を参照してください。

## 7. 任意で AI 向け補足説明を加える

通常の公開では不要です。サイト背景や追加資料を示すなら、最上位に統合します。

```ts
aiReadableContent: {
  notes: '本站记录个人学习过程，内容可能持续修订。',
  links: [{ label: '项目主页', href: 'https://example.com/project' }],
},
```

notes は Markdown、links は label・href を指定します。リンクは公開 HTTP(S) にし、ルートなどの相対 URL はサイト URL 基準で解決します。公開のサイト補足であり、記事本文を置換せず、プライバシー制限にもなりません。

言語別の上書きは `i18n.locales.<コード>.aiReadableContent` を使います。簡体中国語に独自説明を置き、追加リンクを出さない例です。

```ts
i18n: {
  locales: {
    zh: {
      aiReadableContent: {
        notes: '中文内容是作者自己的学习笔记。',
        links: [],
      },
    },
  },
},
```

項目の省略は全体値を継承し、notes: ''・links: [] は該当部分を明示非表示にします。索引、全文、個別 Markdown に入るため公開してよい内容か確認し、変更後は再ビルドします。

## 8. 任意で GA4 を有効にする

既定では Google 統計 script を読みません。必要なら Google Analytics のウェブデータストリームで G- 始まりの Measurement ID を取得します。[Google 公式説明](https://support.google.com/analytics/answer/9539598)も参照できます。数値プロパティ ID、GTM コンテナ ID、その他の識別子は使えません。

site と同じ最上位に統合します。

```ts
analytics: {
  googleAnalyticsId: 'G-XXXXXXXXXX',
},
```

実 ID に変え、空文字で停止します。形式不正は設定エラーです。1 ID で言語別パスを計測でき、テーマ・言語ごとの script は不要です。

本番ビルドかつ ID 指定時のみローダーを出し、dev は送信しません。localhost、そのサブドメイン、ループバックはスキップしますが、LAN IP や外部プレビュー URL の本番ビルドは送信し得るため、全 preview が除外とは限りません。

再配備後に正式 URL を開いて GA4 リアルタイムを確認します。遮断、ネットワーク、統計側設定が影響します。同じ統計を手動・GTM・他注入と重ねないでください。同意管理 UI は付属しないため、必要なら自分で導入します。

## 9. 配備失敗や公開結果がおかしいとき

| 症状                          | 優先して確認                                                                           |
| ----------------------------- | -------------------------------------------------------------------------------------- |
| npm ci の失敗                 | Node・依存要件、package-lock のコミットと package.json との一致。                      |
| 画像 missing／stale／modified | ローカルで元画像・マニフェスト・generated を準備しコミット。配備側で検証を回避しない。 |
| 成功したのに404               | 出力先、ブランチ、ルート、index 対応、未対応サブパス。                                 |
| ホームだけ開き記事再読込は404 | 実静的サブパス、ホームだけの配備、誤った SPA フォールバック。                          |
| CSS・画像・検索不足           | dist 全体の配備、子ディレクトリ漏れ、パス書き換え。                                    |
| canonical・RSS が例ドメイン   | site.url、PUBLIC_SITE_URL、モード別環境値、再ビルドと再配備。                          |
| 設定してもオンライン不変      | 正しいプロジェクト、ブランチ、最新コミットを配備したか。                               |
| 削除後も旧 URL が開く         | 旧成果物、完全置換、ホストのキャッシュ。                                               |
| GA4 データなし                | 実 G- ID、本番ビルド、非ローカル URL、script 遮断。                                    |

日常更新は「ローカル編集・準備 → 検証・プレビュー → ソースのコミット → ビルド・配備」です。更新は[インストールガイド](/ja/blog/starter-guide-1-configure-your-site/)、言語パスは[多言語ガイド](/ja/blog/starter-guide-languages/)を参照してください。
